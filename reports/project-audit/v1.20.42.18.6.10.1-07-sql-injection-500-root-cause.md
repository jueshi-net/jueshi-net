# v1.20.42.18.6.10.1-07 — SQL Injection 500 Root Cause Analysis

## Problem
P3-007 reported "500 error on SQL injection input" during initial audit.

## Investigation

### Test URL
https://i.jueshi.net/ (home page)

### Input Field
Header search input `input[type="text"]` with placeholder "搜索工具…"

### Input Content
`'; DROP TABLE users; --`

### API Called
`/api/search?q='; DROP TABLE users; --`

### Network Response
HTTP 200 — `{"success":true,"data":[]}` (empty results, no error)

### Server Error Log
PM2 logs show NO 500 errors related to search. Only `CredentialsSignin` errors (login failures).

### Root Cause
AUDIT_SCRIPT_BUG — The audit script checked for 500 errors using:
```javascript
const hasError = bodyText2.includes('Internal Server Error') || bodyText2.includes('500');
```
The `bodyText2.includes('500')` check matched any occurrence of "500" in the page text (e.g., phone numbers, prices, postal codes), causing a false positive.

### Is This SQL Injection Risk?
NO. The `/api/search` endpoint:
- Uses Prisma ORM with parameterized queries
- Returns 200 with empty results for SQL injection input
- Does not execute raw SQL
- No server error logged

### Impact on Production
None — the same `/api/search` endpoint exists on production and handles SQL injection input safely.

## Fix
Changed the audit script to check HTTP status code and specific error messages instead of generic `includes('500')`:
```javascript
const hasServerError = bodyText2.includes('Internal Server Error') || 
                       bodyText2.includes('Something went wrong') || 
                       bodyText2.includes('服务器错误');
rec('P3-007', ..., hasServerError || httpStatus >= 500 ? 'FAIL' : 'PASS', ...);
```

## Verification (rerun result)
- P3-007: PASS — HTTP=200, serverError=false

## Severity Reassessment
Downgraded from P1 (security) to AUDIT_SCRIPT_BUG. No security risk exists.

**Classification: AUDIT_SCRIPT_BUG (not a security risk)**
