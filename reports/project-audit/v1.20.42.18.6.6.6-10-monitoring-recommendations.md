# Monitoring Recommendations — v1.20.42.18.6.6.6-10

**Date:** 2026-06-23
**CURRENT_MODE:** AUDIT

> Hermes 提出建议，不擅自安装。所有安装需要用户确认后由 OPS MODE 执行。

---

## P0 — 必须补齐

### 1. Production DB 自动备份
- **现状:** Production 无任何 DB 备份 cron
- **建议:** 复用 staging 的 `scripts/backup-db.sh daily`，在 production 设置 cron `0 2 * * *`
- **原因:** 生产数据库无备份 = 数据丢失风险
- **默认推荐:** 立即部署

### 2. Production 健康检查
- **现状:** Production 无定时健康检查
- **建议:** 复用 staging 的 `scripts/health-check.sh`，在 production 设置 cron `*/5 * * * *`
- **原因:** 服务挂掉无人知道
- **默认推荐:** 立即部署

### 3. Production Fail2ban Nginx 保护
- **现状:** Production Fail2ban 只有 sshd jail，无 Nginx 保护
- **建议:** 添加 nginx-botsearch + nginx-http-auth jail (staging 已有)
- **原因:** 暴力破解 HTTP 认证无防护
- **默认推荐:** 立即部署

### 4. PM2 restart 异常报警
- **现状:** Production PM2 无 restart 监控
- **建议:** 在 health-check.sh 中检查 PM2 restart count > 3/小时 → 报警
- **原因:** PM2 频繁重启 = 应用崩溃循环
- **默认推荐:** 立即部署

## P1 — 建议补齐

### 5. Uptime Kuma 外部可用性监控
- **现状:** 无外部监控
- **建议:** 在 staging 服务器或本地 Mac 安装 Uptime Kuma，每 1 分钟检查 https://jueshi.net
- **优点:** 独立于生产服务器，外部视角可用性监控，支持 Telegram/Email 通知
- **缺点:** 需要额外维护
- **默认推荐:** 安装在 staging 服务器 (192.129.155.149)，端口 3002

### 6. /api/health 健康端点
- **现状:** 无专用 health API 端点
- **建议:** 新增 `/api/health` 返回 `{ status: "ok", db: "connected", uptime: N }`
- **原因:** HTTP 200 ≠ 应用正常，需要 DB 连接验证
- **默认推荐:** 后续开发任务中添加

### 7. Telegram 通知
- **现状:** 无任何通知链路
- **建议:** 使用 Telegram Bot 推送报警 (磁盘 >80%, PM2 restart >3, SSL <14天, 5xx >1%)
- **默认推荐:** 配合 Uptime Kuma 使用

### 8. 磁盘空间报警
- **现状:** 无磁盘监控
- **建议:** health-check.sh 中检查 `df -h /` > 80% → 报警
- **原因:** 磁盘满导致服务崩溃
- **默认推荐:** prod 13%, staging 22%，当前安全但需预警

### 9. SSL 到期报警
- **现状:** certbot 自动续期存在，但无到期预警
- **建议:** health-check.sh 中检查 certbot certificates 到期 <14天 → 报警
- **默认推荐:** 当前所有证书有效期 >50天，但需预防续期失败

### 10. Cloudflare 5xx 监控
- **现状:** 无法验证 Cloudflare 5xx 告警
- **建议:** 用户手动检查 Cloudflare dashboard → Analytics → 是否有 5xx 告警规则；或配置 Cloudflare API token 让 Hermes 查询
- **默认推荐:** 用户手动设置 Cloudflare 告警

### 11. Staging 纳入监控
- **现状:** Staging 有健康检查但无报警
- **建议:** Staging 纳入 Uptime Kuma，报警级别低于 production (staging 挂了不紧急)
- **默认推荐:** 后续优化

## P2 — 可后续优化

### 12. 每周异地备份
- **现状:** Staging 有每日本地备份但无异地
- **建议:** 每周 rsync 备份到另一台服务器或 S3
- **默认推荐:** 后续优化

### 13. 本机监控 + 外部监控分离
- **现状:** 无任何监控
- **建议:** 本机 (health-check.sh) 检查 DB/PM2/Nginx 内部状态；外部 (Uptime Kuma) 检查 HTTPS 可达性
- **默认推荐:** P1 补齐后自然实现

### 14. Nginx 5xx/502 日志监控
- **现状:** 无 Nginx 错误率监控
- **建议:** 定期检查 `grep -c "502\|500" /var/log/nginx/error.log`
- **默认推荐:** 可加入 health-check.sh

### 15. PostgreSQL 连接数监控
- **现状:** 无 PG 连接监控
- **建议:** 检查 `SELECT count(*) FROM pg_stat_activity` > 阈值 → 报警
- **默认推荐:** 后续优化
