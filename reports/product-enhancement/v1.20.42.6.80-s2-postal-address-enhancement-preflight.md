### 互补关系

- **Postal Code**: 专注于邮编查询和验证，有丰富的邮编数据库
- **Address Formatter**: 专注于地址格式化，有完整的表单和模板

### 当前不足

3. **功能分散**: 用户需要在两个工具间切换

## 四、S2 MVP 目标定义

### 建议方案：在 Address Formatter 中增强"地址解析"功能

**理由**:
1. Address Formatter 已有完整的地址字段结构
2. Postal Code 专注邮编查询，不宜增加复杂解析逻辑
3. 地址解析是用户高频需求（粘贴客户地址 → 自动拆分）

### 最小实现目标

1. **地址解析输入区**
   - 大文本框，用户粘贴完整地址
   - "解析地址"按钮

2. **智能解析引擎**（纯前端，不依赖外部 API）
   - 识别国家/地区（关键词匹配）
   - 识别邮编（正则匹配）
   - 识别电话（正则匹配）
   - 识别省/州（关键词匹配）
   - 识别城市（关键词匹配）
   - 剩余部分作为地址行

3. **解析结果展示**
   - 字段化展示（可编辑）
   - 英文格式地址
   - 中文格式地址
   - 邮编高亮（如识别到）
   - 缺失字段提示

4. **复制功能增强**
   - 复制英文地址
   - 复制中文地址
   - 复制字段化结果（JSON）

5. **Shipping Calculator 联动**
   - "继续计算运费"按钮
   - 通过 localStorage 传递：国家、城市、邮编、地址摘要
   - 不影响 Container → Shipping 已上线联动

### 不做的事情

- ❌ 全球邮编数据库
- ❌ 外部 API 调用（Google Maps API 等）
- ❌ 100% 准确保证
- ❌ 保存到服务器
- ❌ 保存到 Workspace
- ❌ 新增数据库
- ❌ 新增 migration

## 五、推荐实现方案

### 方案 A：增强 Address Formatter（推荐）

**优点**:
- 复用现有表单结构和国家配置
- 用户流程清晰：粘贴 → 解析 → 编辑 → 格式化 → 复制
- 不影响 Postal Code 的稳定性

**缺点**:
- 需要新增解析逻辑
- 需要处理中英文地址混合情况

### 方案 B：新建独立工具 Address Parser

**优点**:
- 功能独立，不干扰现有工具
- 可以专注做解析

**缺点**:
- 增加工具数量
- 用户需要在多个工具间切换
- 与 Address Formatter 功能重叠

### 方案 C：合并 Postal Code 和 Address Formatter

**优点**:
- 单一工具，功能完整

**缺点**:
- 破坏现有 URL 和 SEO
- 影响已收藏用户
- 风险高

**推荐**: 方案 A — 在 Address Formatter 中增强地址解析功能

## 八、与 Shipping Calculator 联动建议

### 方案比较

| 方案 | 说明 | 优先级 |
|---|---|---|
| A. Address → Shipping | 带入国家/城市/邮编 | ✅ 推荐 |
| B. Address → Commercial Invoice | 带入收件人信息 | ⚠️ 后续考虑 |
| C. Address → Quote Sheet | 带入地址信息 | ⚠️ 后续考虑 |
| D. Address → TaskChain | 通用上下文 | ✅ 已有 |

### 推荐实现：Address → Shipping Calculator

**传递数据**:
```typescript
interface AddressToShippingPayload {
  source: 'address-formatter';
  version: 1;
  createdAt: string;
  expiresAt: string;  // 30 分钟
  consumed: boolean;
  payload: {
    country: string;
    city: string;
    postalCode: string;
    addressSummary: string;  // 街道地址摘要
  };
}
```

**localStorage Key**: `jueshi.addressToShipping.v1`

**Shipping Calculator 侧**:
- 检测中转数据
- 显示提示："已从地址助手带入目的地信息"
- 不自动预填复杂数据
- 用户可手动确认或忽略

**与 Container → Shipping 的关系**:
- 两者独立，不冲突
- Container → Shipping 传递：体积、重量、件数
- Address → Shipping 传递：目的地国家、城市、邮编
- 如两者都有数据，Shipping Calculator 可合并显示

## 九、边界与风险

### 明确不做

| 不做 | 原因 |
|---|---|
| 全球邮编数据库 | 数据量大，维护成本高 |
| 外部 API 调用 | 依赖第三方，可能收费 |
| 100% 准确保证 | 地址格式多样，无法完全覆盖 |
| 保存到服务器 | 隐私风险，增加成本 |
| 保存到 Workspace | 本轮范围外 |
| 新增数据库 | 无需持久化 |
| 新增 migration | 无需 schema 变更 |

### 风险

| 风险 | 缓解措施 |
|---|---|
| 解析不准确 | 明确提示"仅供参考"，字段可编辑 |
| 中英文混合地址 | 优先识别英文格式，中文作为备选 |
| 未知国家地址 | 提示"未识别国家"，用户手动选择 |
| 隐私泄露 | 纯前端处理，不上传服务器 |

### 不影响

| 工具/功能 | 影响 |
|---|---|
| Container → Shipping | ❌ 不影响 |
| Commercial Invoice | ❌ 不影响 |
| Quote Sheet | ❌ 不影响 |
| Workspace 单据复用 | ❌ 不影响 |
| HS Code | ❌ 不影响 |
| 9833416@qq.com | ❌ 不影响 |
